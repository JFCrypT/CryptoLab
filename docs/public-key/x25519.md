# X25519 key agreement

CryptoLab uses `cryptography` for X25519. It does not implement Curve25519 scalar
multiplication manually.

X25519 provides elliptic-curve Diffie-Hellman key agreement with 32-byte private keys,
32-byte public values, and a 32-byte raw shared secret. The raw shared secret is not used as
a session key directly. CryptoLab passes it to HKDF-SHA-256 with explicit `salt`, `info`,
and output length parameters.

## Local key generation

```bash
cryptolab public-key x25519 generate \
  --private-key-out alice-x25519-private.pem \
  --public-key-out alice-x25519-public.pem
```

Private keys use unencrypted PKCS#8 PEM and file mode `0600`. Public keys use
SubjectPublicKeyInfo PEM and mode `0644`.

## Reproducible two-party exchange

The exchange command accepts either two PEM private-key files or two raw 32-byte private
keys. It derives both public keys, computes the shared secret independently on each side,
checks equality, rejects the all-zero result, and applies HKDF-SHA-256.

```bash
cryptolab --explain public-key x25519 exchange \
  --alice-private-key-file alice-x25519-private.pem \
  --bob-private-key-file bob-x25519-private.pem \
  --info-text "CryptoLab X25519 session" \
  --length 32
```

Raw hexadecimal inputs exist for published-vector validation and reproducible examples.
They are not a recommendation to expose private keys on a shell command line in real
systems.

## Authentication limitation

X25519 establishes a shared secret but does not authenticate participants. A real protocol
must authenticate the exchange or its transcript. Applying HKDF does not repair an
unauthenticated exchange.

## Comparison with finite-field Diffie-Hellman

```bash
cryptolab --explain public-key compare-key-agreement
```

The comparison covers mathematical setting, public-value representation, KDF processing,
authentication, implementation category, and limitations. It does not declare either
construction universally superior outside a concrete protocol and threat model.
